# LCAgent 智能体架构技术方案

## 1. 目标与结论

LCAgent 采用“两类模型、一个决策智能体、三类数据系统、一个确定性执行层”的架构：

- 决策模型：完成任务分析、工具选择、结果判断和 Python 任务脚本编写。
- Embedding 模型：只完成文档切片和查询文本的向量化。
- 资源注册表：保存 UE 权威扫描结果、文件夹层级用途报告及用户批准状态。
- 对话上下文：保存完整原始对话，并用结构化快照压缩较早历史。
- 文档知识库：保存用户上传文档的原文、切片、向量和引用元数据。
- 确定性工具层：负责检索、脚本安全校验、原子写入、dry-run 和 UE 通信。

旧的 RetrievalAgent 和 CodingAgent 不再调用独立大模型。检索不是一个需要“思考”的角色，编码能力也直接归入决策模型。`RAG_path.py` 和 `RAG_memory.py` 暂时保留用于兼容与数据迁移，但不进入新主链路。

## 2. 总体架构

```text
用户 / Electron UI
        |
        +-- 普通对话 -----------------------> 决策模型
        |                                      ^
        |                                      |
        |                            原始历史 + 压缩快照
        |
        +-- 智能体任务 -> SceneGoalSpec 草案 -> 用户审核冻结
                              |
                              +-- ObservationPlan（确定性编译）
                              |
                              +-- TaskOrchestrator -> 决策模型（规划 + 编码）
                              |
                              +-- search_assets ----> 资源注册表
                              +-- search_knowledge -> 文档知识库 -> Embedding 模型
                              +-- write_script -----> AST 校验 + 原子写入
                              +-- execute_script ---> dry-run / UnrealMCP
                                                       |
                                               UE 插件 Handler
```

这里的“单决策模型”指一次任务中只有一个聊天模型身份。状态机可以多次调用该模型，但不会把任务转发给第二个检索模型或编码模型。

## 3. 状态机

主状态为：

```text
ANALYZE
  |-- search_assets / search_knowledge --> RETRIEVE --> OBSERVE --+
  |-- write_script ----------------------> GENERATE -> VALIDATE ---+--> ANALYZE
  |-- execute_script --------------------> EXECUTE ---> OBSERVE ---+
  |-- 非法 JSON、参数或工具失败 ----------> REPAIR -----------------+
  +-- finish -----------------------------------------------------> FINISH
```

决策模型每一步只能返回一个 JSON 对象：

```json
{
  "action": "search_assets",
  "arguments": {
    "query": "山地地形材质",
    "asset_class": null,
    "limit": 10
  },
  "rationale": "创建脚本前需要取得用户确认过的 UE 对象路径"
}
```

可用动作只有：

| 动作 | 作用 | 是否由大模型执行 |
|---|---|---|
| `search_assets` | 检索已确认且仍存在的 UE 资源 | 否 |
| `search_knowledge` | 向量检索上传文档 | 否 |
| `write_script` | 写入模型生成的 `generated_*.py` | 模型生成内容，运行时校验和写入 |
| `execute_script` | 运行受控脚本 | 否 |
| `finish` | 返回最终答复 | 是 |

模型输出无法解析、动作越权、缺少参数或工具报错时进入 `REPAIR`。错误以结构化观察结果返回给同一决策模型。默认最多 12 次模型调用和 3 次修复，防止失控循环。

### 3.1 SceneGoalSpec 与 ObservationPlan

自然语言需求不会直接成为执行成功标准。决策模型先生成 `SceneGoalSpec` 草案，模型无权批准草案；用户审核后使用内容哈希冻结目标。约束包含 `required_observations`，`ObservationPlanner` 据此合并相同实体选择器、去重字段，并生成最小查询集合。

细粒度属性路径与 UE 查询投影分离。例如约束需要 `transform.location.x`，证据要求保留完整属性路径，实际查询只请求顶层 `transform`。受保护实体即使没有显式约束，也会自动要求 `identity`、`transform`、`bounds`、`asset_reference` 和 `tags`，避免把未观测误判为未改变。

目标契约、审核冻结、观测计划和能力预检均已完成。离线场景链路可以使用固定 UE 响应页或 Fake UE 生成快照并走完整验证闭环；通用 `query_scene_state` 的真实返回仍属于下一阶段 UE 插件改造。

### 3.2 SceneSnapshot、SceneDiff 与确定性验证

`SceneSnapshotBuilder` 把分页查询结果规范化为带单位、坐标系、稳定实体 ID 范围和完整性声明的 `SceneSnapshot`。它不会为 UE 没有返回的属性填伪默认值。`SceneDiff` 按稳定 ID 对齐实体并应用数值容差；分页截断、单位不一致、坐标系不一致或字段集合不匹配时，结果为 `inconclusive`，而不是错误地报告“没有变化”。

`ConstraintEngine` 不调用模型，按注册 evaluator 计算 `entity_exists`、`entity_count`、`entity_type`、属性相等/包含/范围、资源引用、几何非重叠和保护对象约束。每个结果保存测量值、期望值和证据引用，并明确区分 `passed`、`failed`、`not_observable`、`error` 和 `skipped`。

### 3.3 受限修复和终止条件

`RepairScopeController` 只根据失败约束的依赖关系推导允许修改的实体、操作和属性。模型提出修复动作后，系统在执行前检查声明写集合；执行后再用真实 `SceneDiff` 检查实际变化。受保护对象变化、越权属性修改和未声明写入都会阻止成功。

`TaskOrchestrator` 分开计算执行错误修复与目标不满足修复的预算。模型返回空动作或 `finish` 不等于任务成功；只有重新观测后的确定性验证报告通过，运行才能以 `goal_satisfied` 终止。当前 Fake UE 已覆盖“一次执行不满足、一次受限修复后通过”的 Actor X 坐标闭环。

## 4. 三类数据系统

### 4.1 UE 资源注册表

资源路径不是普通语义知识，不能仅靠向量相似度决定是否可执行。注册流程分为三步：

1. UE `AssetRegistry` 扫描给出权威对象路径、资源名和资源类型。
2. 系统把资产聚合为完整文件夹树，决策模型逐层判断大文件夹及其下级文件夹用途。
3. 用户审核一份文件夹注册报告；批准后，目录语义下发到其直属资产。

状态机执行态的 `search_assets` 默认只返回：

- `user_status = confirmed`；
- `exists_in_project = true`；
- 当前工作区注册表中的资源。

再次扫描时，系统生成新增、移除及资产数量变化报告。报告批准前沿用上一版已批准分类；已从 UE 扫描结果中消失的资源会立即标为 `missing`，即使过去确认过也不会再提供给任务执行。

UnrealMCP 新增只读命令：

```json
{
  "protocol_version": "1.0.0",
  "request_id": "asset-scan-...",
  "type": "scan_project_assets",
  "params": {
    "package_roots": ["/Game"],
    "max_results": 10000
  }
}
```

Handler 仅调用 UE `AssetRegistry`，不加载、创建或修改资源。响应中的 `result.assets` 会进入本地 SQLite 注册表。

### 4.2 用户交互上下文

对话系统不使用向量库恢复当前上下文，而采用：

```text
系统消息 + 结构化压缩快照 + 最近若干轮原始对话
```

完整原始消息始终保留。达到模型档案设定的上下文阈值后，系统调用当前决策模型更新结构化快照。压缩失败时保留旧快照并使用安全降级上下文，不删除历史。

### 4.3 文档知识库

每个工作区可以创建多个知识库，并上传：

- PDF：按页解析，引用保留页码；
- DOCX：读取段落并保留标题；
- TXT：支持 UTF-8/GB18030；
- Markdown：按标题保留章节锚点。

当前切片策略为确定性的字符窗口：默认 1000 字符、150 字符重叠，并优先在段落或句子边界切分。原文件 SHA-256 用于知识库内去重。

索引记录保存使用的 `embedding_profile_id`。查询必须使用同一档案；不同模型或维度的向量不会混合比较。检索结果包含文件名、页码/标题、切片文本和余弦相似度，可直接用于最终引用。

## 5. 双模型网关

### 5.1 对话/决策模型

由 `model_gateway.py` 管理，支持 DeepSeek、OpenAI 和 OpenAI 兼容接口。模型档案保存非敏感配置，API Key 只保存在 Git 忽略的 `.env` 中。

### 5.2 Embedding 模型

由 `embedding_gateway.py` 独立管理。Embedding 档案包括模型、Base URL、密钥环境变量、可选维度、批大小和超时设置。它不复用对话模型参数，也不参与状态机决策。

## 6. 生成脚本与执行边界

决策模型可以编写代码，但不能直接执行任意 Shell。`ExecutionRuntime` 强制：

- 文件名必须为 `generated_*.py`，且只能位于 `LCA` 脚本目录；
- 写入前执行 Python AST 语法与安全校验；
- 禁止生成脚本导入 `socket`、`subprocess`、`shutil`、`ctypes`；
- 禁止 `eval`、`exec`、`compile`、`__import__`；
- 地形脚本必须复用 `create_terrain` 或 `terrain_client`；
- 每次任务维护独立的资源路径授权集合；脚本或参数中的 UE 对象路径必须先由本次 `search_assets` 返回；
- 通过临时文件和原子替换写入；
- 使用参数数组和 `shell=False` 运行；
- 默认追加 `--dry-run`，只验证 Python 和最终 JSON，不连接 UE。

切换到 live 模式需要 UI 中额外确认。只有真实返回 `status=success` 且进程退出码为 0，状态机才可以把任务描述为执行成功。

## 7. 本地数据与隔离

```text
LCA/model_profiles.local.json          对话模型非敏感配置
LCA/embedding_profiles.local.json      Embedding 非敏感配置
LCA/.env                               API Key
LCA/workspaces.local.json              工作区列表
.codex_tmp/workspace_chats.json        原始对话与压缩快照
.lca_data/workspaces/<workspace_id>/
  knowledge/knowledge.db               文档、切片和向量
  knowledge/originals/                 上传原文
  resources/resources.db               UE 资源注册表
  resources/folder_report_*.json       文件夹报告草稿与已批准版本
  goals/goal_*.json                    SceneGoalSpec 草案或冻结目标
  goals/observation_plans/*.json       确定性观测计划
  scene_records/snapshots/*.json       标准化场景快照
  scene_records/diffs/*.json           场景差异
  scene_records/validations/*.json     确定性验证报告
  scene_records/repair_scopes/*.json   修复权限范围
.lca_data/lca.db                       任务运行、事件和产物索引
.lca_data/runs/<run_id>/artifacts/     模型轨迹和运行结果
.lca_data/runs/<run_id>/exports/       带 SHA-256 清单的复现实验包
<UE工程>/.lcagent/
  resource_registry_report.json        工程内结构化报告
  resource_registry_report.md          工程内可读报告
```

这些运行数据均不提交到 Git。`workspace_id` 由规范化工作区路径计算，因此不同 UE 工程互不共享资源路径和知识库。

## 9. 验证边界

当前可以在不启动 UE 的情况下自动验证：

- 模型档案与密钥隔离；
- 文档解析、切片、去重、向量检索和引用；
- 资源注册、人工确认、失效处理和检索白名单；
- 状态转换、错误修复和最大步数；
- 生成 Python 的 AST 安全约束；
- dry-run 生成的 JSON；
- SceneSnapshot、SceneDiff、ConstraintEngine 和 RepairScope；
- Fake UE 的一次失败、一次受限修复、最终通过闭环；
- 运行 ZIP 导出、脱敏与逐文件哈希；
- Electron 类型检查与生产构建。

仍需人工完成：

1. 使用 VS2022 编译 UnrealMCP 插件；
2. 打开 UE 后验证 `scan_project_assets` 返回实际工程资源；
3. UE 插件实现通用只读 `query_scene_state` 并验证分页、单位和稳定 ID；
4. 验证具体对话模型和 Embedding 服务的真实 API；
5. live 模式下验证 Actor、地形、道路、河流的最终 UE 效果。
